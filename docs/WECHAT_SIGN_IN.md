# WeChat website sign-in and registration

WeChat **login** is separate from the Stripe WeChat Pay payment method. The existing Stripe approval does not supply a WeChat login AppID or AppSecret. This integration uses an approved WeChat Open Platform **Website Application / 網站應用**, `snsapi_login`, and the hosted QR-code authorization screen. It does not create an Open Platform account, pay a verification fee, or claim that WeChat has approved the site.

## Operator setup

1. Sign in to [WeChat Open Platform](https://open.weixin.qq.com) with the actual business/developer account. Complete the qualification verification required by its console. Use the applicable Hong Kong/overseas business process if offered; qualification, document, registration and fee requirements are controlled by WeChat. Do not invent a mainland company, business licence, ICP filing or approval.
2. In Management Centre, create or open a **Website Application**, using the LingYing business details and website `https://lingyingdrama.com`. Supply the real documents and any domain-verification file WeChat requests. Apply for **WeChat Login** and wait for approval. A payment merchant account, Mini Program or mobile-app AppID is not this website application.
3. Set the **authorization callback domain / 授權回調域** to `lingyingdrama.com`, without `https://`, a path or `www`. The application sends this exact callback URL:

   `https://lingyingdrama.com/api/auth/wechat/callback`

   Public terms: `https://lingyingdrama.com/terms`; privacy: `https://lingyingdrama.com/privacy`.
4. In **Cloudflare → Workers & Pages → lingying → Settings → Variables and Secrets**, add both approved credentials as encrypted **Secrets**: `WECHAT_APP_ID` and `WECHAT_APP_SECRET`. Save/deploy the settings on this existing Worker. Do not paste the AppSecret into chat, Git, browser code, `.dev.vars` commits or logs. Keep Stripe and Google/Apple secrets, `STRIPE_TEST_MODE`, APP namespace, MEDIA bucket and payout settings unchanged.
5. Enable the existing account-email delivery service using [email setup](EMAIL_AUTH.md), including a verified sender and its encrypted sending credential. New WeChat registration requires an inbox code; the live site reported `auth.email=false` during implementation. Existing linked sign-in does not require sending an email. Existing-account linking requires verified contact email and the current LingYing password.
6. `/api/config` exposes only `auth.wechat`. Missing, partial or malformed credentials leave the button disabled and the start route unavailable. A valid configured pair enables the route; this flag establishes configuration presence, not approval or a completed real sign-in. Open `/auth`, choose WeChat, scan the QR code with the phone's WeChat, and approve. Verify the return to `lingyingdrama.com` before reporting actual provider success.

This is website **QR login**. Desktop browser users scan with their phone. Do not advertise one-tap sign-in inside WeChat's own mobile browser or a native app: those can require a separately approved Official Account/mobile integration and are not implemented here. Email/password and existing Google/Apple methods remain available as configured.

## New and existing users

- An existing WeChat identity signs into the same LingYing account. The application rotates the browser session without changing purchases, balances, creator status or account profile edits.
- A newly authorized WeChat identity first sees **Finish your WeChat registration**. WeChat does not provide an email, so the person enters a real contact email and display name and explicitly accepts the site terms. No account, wallet, purchase or financial credit is created merely by scanning. The person requests a six-digit email code and enters it in the same registration browser. Only then is the account/identity created and the contact email marked verified. The account is created with a disabled password credential; subsequent WeChat login does not ask for a LingYing password.
- WeChat itself never verifies a supplied email. Registration requires the separate inbox code and stays blocked while account-email delivery is unavailable; no account or sign-in session is created on a delivery failure. A verified owner email is still required by existing configured-administrator rules. WeChat profile names and email input cannot grant privileges.
- If the email already belongs to an account, the registration is rejected without accessing or merging that account. The owner signs in through its existing method and explicitly connects WeChat from **Account → Sign-in methods → Connect WeChat**, confirming the current LingYing password and a verified account email. This password-confirmation linking route is for accounts with a password; existing provider-only accounts continue using their configured sign-in method. No automatic email, nickname or UnionID merge is performed.
- Identity-provider identifiers are private. `/api/account/identities` exposes only whether WeChat is linked; no OpenID, UnionID, AppSecret or provider tokens are returned to the browser.

## Security and storage

The additive `wechat_identities` table pins identity to `(app_id, open_id)`, one identity per LingYing user, and validates optional UnionID consistency. AppID changes do not silently migrate old identities. `wechat_oauth_attempts` stores hashed state/browser bindings, the exact initiating session, app, safe return path and a ten-minute expiry. A callback consumes a matching attempt atomically before exchanging its code. Session changes/revocation during provider calls, wrong browser cookies, replays, expired states and conflicting identities are rejected.

Token and profile calls use only the pinned HTTPS WeChat endpoints, bounded response bodies, a ten-second timeout and no redirects. WeChat's token endpoint requires AppSecret in a server-side query; do not log its URL, raw errors or response. Validate scope, OpenID and UnionID, then discard access/refresh tokens. The application does not request WeChat messages, contacts or payments for login.

`wechat_registrations` stores the short-lived pending identity and safe destination behind a separate random HTTP-only, Secure, SameSite=Lax cookie. No provider identifier or registration bearer token is placed in a browser URL or JavaScript-readable storage. The separate `wechat_registration_codes` table stores only a cookie/email-bound code hash, expiry and attempt count. Registration consumes both browser and inbox proofs, inserts user/identity and records the separately verified contact email atomically; forged profile fields, concurrent retries and email collisions cannot create extra accounts. Five incorrect code attempts exhaust a proof; the counter commits even on rejection. Sending is limited to one message per minute per ticket/address, five per hour per hashed address and the endpoint IP limit. Existing email collisions never receive a WeChat signup code. Failed delivery deletes that code without creating an account. Expired authorization records are unusable and are cleaned up by later WeChat starts; expiry is not a claim of instant physical erasure.

The policy version `2026-11-09`, effective 9 November 2026, explains optional WeChat identity data, separate email collection and short-lived cookies in English and both Chinese policy versions. Existing Pass acknowledgements and payments keep their actual versions; new Pass checkout requires the current shared policy version. Pass pricing, limits and financial partitions remain intact.

## Validation

Run `npm test`, `npm run build:cloudflare`, the WeChat/existing account and legal Playwright suites, and `npm run test:cloudflare`. Cloudflare smoke consumes the required build outputs and uses a temporary local-only configuration without the deployment rebuild hook, so emulator restarts preserve the same validated artifacts. Local fixtures cover provider response validation, browser/state binding, expiry, duplicate callbacks, registration, explicit linking, email collisions, session revocation during an exchange, privacy, translations and preservation of account balances. Tests mock WeChat and use disposable local data; they never fabricate a production login, create a real WeChat account, send a real security email or charge money.

As of implementation, no `WECHAT_APP_ID` or `WECHAT_APP_SECRET` binding was present on the existing Worker. Configuration/deployment and local tests do not establish real WeChat approval or completed user authorization.

Provider references: [WeChat website-login guide](https://developers.weixin.qq.com/doc/oplatform/Website_App/WeChat_Login/Wechat_Login.html), [Tencent CloudBase WeChat login](https://docs.cloudbase.net/authentication-v2/method/wechat-login). WeChat's direct developer documentation returned HTTP 403 in this execution environment; the console and current provider documentation remain authoritative for application eligibility and approval.
